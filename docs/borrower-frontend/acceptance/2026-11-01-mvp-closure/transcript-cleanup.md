# Synthetic test transcript cleanup

Part B of the MVP closure. Owner-approved removal of the test-generated assistant transcripts from the
disposable borrower account, with a per-record revalidation, a reversible export, document-API
deletion, and verification on both the API and the rendered page.

Site `loanportal.local` (database `_21ddc3370f18f30e`), account `review.demo@example.invalid`,
captured 2026-11-01. Evidence in [`transcripts/`](transcripts/) and
[`database/counts-after-transcript-cleanup.txt`](database/counts-after-transcript-cleanup.txt).

## 1. What was reported, and what was actually there

The findings-closure bundle reported 103 conversations and 242 messages. Re-measured independently at
the start of this task, the scope had grown — the earlier report was accurate for its moment, and the
extra rows came from the acceptance runs that followed it:

| | Reported earlier | Measured now |
| --- | ---: | ---: |
| Advisory Conversation, all owners | 138 | **163** |
| …owned by `review.demo@example.invalid` | 138 | **141** |
| …of those, created on/after 2026-11-01 | 103 | **124** |
| Advisory Message rows under those | 242 | **290** (145 user + 145 assistant) |

`Advisory Message` is a **child table** of `Advisory Conversation` (`istable: 1`, parent field
`messages`, `autoname` on the conversation is `field:thread_id`), so a conversation is the document and
its messages are rows inside it. That is why the deletion is one document per thread, and why no
orphaned message row can survive it.

## 2. Revalidation, per record

[`transcripts/synthetic_transcripts.py`](transcripts/synthetic_transcripts.py) (`--mode classify`)
loads every candidate through the document API and records the owner, user, customer, application,
thread id, creation/modified, turn count and the full message list. It then applies one rule:

> A conversation is a test artefact only when **every** user message in it appears verbatim in a
> harness or fixture source.

The corpus is code, not prose: `tests/e2e/*.cjs`, `tests/e2e/*.py`, the harness scratch scripts under
`tests/e2e/out/`, `tests/e2e_seed.py` and `tests/utils.py` — 33 files. It deliberately excludes this
bundle's own documents, so a prompt cannot be attributed to a test by citing a report that quotes it.
The per-prompt result is [`transcripts/prompt-attribution.json`](transcripts/prompt-attribution.json):
13 distinct prompts, 9 located, 4 not.

| Candidate conversations (124) | Count | Disposition |
| --- | ---: | --- |
| every user prompt located in a harness source | **111** (224 messages) | deleted (§4) |
| at least one prompt not locatable | **13** (66 messages) | **preserved and reported** |
| other owners | 22 | untouched |
| same owner, created before 2026-11-01 | 17 | untouched (outside the approved cutoff) |

Every record in the deletion set was also checked for association before deletion:
`user = review.demo@example.invalid`, `customer = Review Demo Borrower`,
`application = ACC-LOAP-2026-00018`, `owner = review.demo@example.invalid` — no exceptions
(`deletion-manifest.json`).

### Why the 13 preserved records stayed

Four prompts could not be placed in any harness source, and the same 13 conversations carry **no**
fixture reply — their assistant side is live-model text (`Bajaj Finance states that a minimum CIBIL…`,
`I've passed this to a human reviewer…`, `What-if only (your application and decision are unchanged)…`),
while 100 of the 111 deleted ones contain the stub's `Acceptance fixture response:` wording.

Two of the four prompts are generated by the product itself, not by a test:
`What if my credit score was 800, my monthly income was 90000, my monthly obligations were 5000 and my
employment tenure was 60 months?` is built by
[`what-if-form.tsx:19`](../../../../apps/web/assistant/src/what-if-form.tsx#L19) from form values, and
`What does the lending policy say about the minimum credit score?` is a typed question. Two more are
single, plainly human-phrased requests (`I want to speak to a human advisor about this decision.`,
`The income recorded on my application is wrong. I want to dispute it.`).

Their creation window is 17:02–17:34 UTC, before the acceptance runs that produced the rest. They may
well be manual product-experience sessions on the demo account. "Belongs to the demo borrower" is not
the same as "was created by a test run", so they were kept and are listed by id in
[`transcripts/classification-detail.json`](transcripts/classification-detail.json).

## 4. Deletion

Same script, `--mode delete`, reading the manifest it exported. Before deleting anything it
**re-derives the classification** and refuses if the candidate set changed or if any manifest id is no
longer conclusive ([`transcripts/delete-result.json`](transcripts/delete-result.json)).

Mechanism: `frappe.delete_doc("Advisory Conversation", name, ignore_permissions=True,
delete_permanently=False)` per thread — the document API, normal hooks, child message rows deleted with
the parent, and `delete_permanently=False` so a recoverable snapshot lands in `tabDeleted Document`.
No SQL, no table surgery.

One correction worth recording: the first attempt passed `delete_children=True`, which is not a
parameter of `delete_doc` in Frappe 16. Every record failed cleanly, **nothing was deleted** (counts
identical, `stillPresent` = all 111, failures listed rather than swallowed), the signature was read
from the installed source, and the retry succeeded.

| Advisory Message | 352 | **128** |
| Messages under the cutoff set | 290 | **66** |
| Orphaned message rows | 0 | **0** |
| Deleted Document snapshots | 27 | **138** (+111) |

Deleted: 111 conversations, 224 child messages, 0 failures.

## 6. Stopping the next run from leaving this behind

The transcripts survived because
[`e2e_seed.teardown`](../../../../apps/loan_advisory_portal/loan_advisory_portal/tests/e2e_seed.py#L181-L215)
deleted applications, profiles and users but never conversations, and never the fixture customers. Both
omissions are now fixed in the teardown: it removes each fixture borrower's `Advisory Conversation`
documents (their messages go with them) and then the `Customer` rows it created, and reports
`conversationsRemoved` / `customersRemoved`.

Proved live, not by inspection
([`transcripts/teardown-hygiene-demo.json`](transcripts/teardown-hygiene-demo.json)): seed `hygiene1`,
create a conversation with two messages for that borrower through the document API, run the teardown →
`conversationsRemoved: 1`, conversations for the user 1 → 0, messages 2 → 0, profile and user gone,
site-wide orphan messages 0.

Two residue items this task created and then removed, recorded because they were persistent writes at
the moment they existed: the `nvda1` fixture (seeded for the deferred screen-reader journeys, torn down)
and four `Customer` rows those two seeds left behind before the teardown fix landed. They were deleted
only after each was verified unreferenced by any Borrower Profile, Loan Application, Account Invitation
or Advisory Conversation
([`database/fixture-customer-cleanup.json`](database/fixture-customer-cleanup.json)); the `closure1`
customers from the previous task are referenced and were left alone. Customer count is back to the
baseline 15.

No test-account feature was added and no account was permanently labelled: the scope was the identified
records plus the teardown that stops the pattern repeating.
