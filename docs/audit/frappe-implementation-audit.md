Verified directly from current source and current local runs:

- The seven custom DocTypes, the roles, the custom Loan Application fields and the install/migrate path.
- Every borrower-facing Frappe method: ownership resolution, session handling, invitation lifecycle, document handling, feedback, conversation bookkeeping, assertion minting, LiveKit token minting and the voice exchange.

- The Node runtime gateway, the React island, thread handling and the proxy harness.
- The current test suites and the current Git state.

Not verified in this audit:

- **No live LiveKit room, transcript flow or browser voice session** was run. The execution report says the same.
- **No browser E2E run** was repeated. The report's 36/36 journey checks and 39/39 security checks are historical claims, not evidence produced by this audit.
- **No production deployment, production proxy, multi-worker FastAPI deployment, Redis instance, SMTP server, identity provider or load test** was exercised.
- **No external LLM, Langfuse, bureau provider or LiveKit service** was contacted.
- `p1loan.local` was not read or changed.

Consequently, statements in this document about live behavior are labeled as such. Where the execution report's number could be reproduced locally, the reproduced number is quoted in §4 and supersedes the historical figure for audit purposes.

## 3. Findings by category

### 3.1 Missing functionality

- **F-M01 — Voice surface is absent.** There is no voice consent, permission request, connecting/connected/listening/speaking/muted/reconnecting/ended UI, no mute or hang-up controls, no transcript display and no return-to-text path. `Voice Session` and token minting exist server-side only. `api/livekit.py`, `api/voice.py`, `services/livekit_token.py`; execution report §5.
- **F-M02 — Conversation history and resumption are absent.** `list_conversations` and `record_turn` exist in `api/agent.py` but have no production caller; the island clears state on ready and starts a fresh conversation. There is no authorized history list, no resume, no application-context restoration and no way to switch application without leaking prior context.
- **F-M03 — Password reset and email verification do not exist.** Invitations are handed over by an operator. This is an owner decision, not an implementation bug, but it blocks the public/account screen group.
- **F-M04 — Several required screens have no route or no distinct state.** Missing as dedicated surfaces: landing/public product view, registration success/verification state, suspended/disabled and session-expired pages (only a blocked card/redirect exists), terms/privacy, contact/help, notification preferences and notification centre, support/FAQ, product listing/detail, correction/resubmission after `INFO_REQUESTED`, processing/pending/manual-review presentation, rejection explanation beyond customer-visible failing reasons, eligibility insights, a dedicated what-if screen, improvement recommendations and reapplication guidance. Some content is partially present inside the application detail or the agent tools, but not as the screens the brief enumerates.
- **F-M05 — No inbound Lending state synchronization.** The portal writes `custom_lifecycle_state`; native `status` is written only for APPROVED/REJECTED and only while `docstatus == 0`. A submitted application that is withdrawn shows `WITHDRAWN` in the portal while native `status` remains `Open` to Desk users. No process maps Lending-side changes back to the portal.
- **F-M06 — No state-transition audit history.** Timeline entries are synthesized from `custom_submitted_at` and decision timestamps, not from an immutable transition log.
- **F-M07 — No rate limiting on borrower methods.** Only invitation validate/redeem are rate-limited. Chat, bureau, mint, document operations and feedback have no per-user or per-IP budget (global admission control is a concurrency cap, not abuse control).

### 3.2 Incorrect assumptions

- **F-A01 — "Duplicate responsibilities remaining: none identified" is not supported.** Two lifecycle vocabularies exist (`DRAFT`-first portal select in `install.py:9-20` versus canonical `STATES` without `DRAFT` in `application/lifecycle.py:39-59`); conversation bookkeeping is duplicated between the live mint path and dead `record_turn`/`list_conversations`; and the FastAPI process uses one Frappe credential for both read and privileged evidence write.
- **F-A02 — Per-process replay is framed as an "unverified integration" rather than a correctness/security defect.** The execution report §10 lists "horizontal scaling of the assertion verifier" among unverified integrations. In a two-worker deployment the single-use guarantee is broken today, so this is a blocking P0, not a scaling nicety.
- **F-A03 — "Agent Integration for the voice worker (read-only on evidence)" understates the write path.** The role is genuinely read-only, but evidence writes are performed by the FastAPI sink using the general client credential. The report's permissions sentence and the evidence path therefore describe different identities.
- **F-A04 — "Conversation ownership: foreign thread join and record_turn are 403" is true but narrow.** Ownership is enforced at mint time; the AG-UI layer then consumes the client-supplied thread id without checking it equals the asserted thread, and an existing thread can be rebound to a different application owned by the same borrower.
- **F-A05 — "Verified at 390 × 844" is not responsive verification across the required widths.** Tablet and desktop widths, assistive technology and automated axe checks were not measured.
- **F-A06 — The browser suites were run once and are reported as standing assurance.** They are not part of the reproducible default suite and were not rerun in this audit.

### 3.3 Security weaknesses

- **F-S01 (Critical) — Process-local replay cache.** `ReplayCache` (`api/assertion.py:45-70`) is a per-process dictionary guarded by a thread lock. Two uvicorn workers each accept the same `jti`; a restart forgets claims; there is no shared atomic insert-if-absent with expiry and no fail-closed behavior if a shared store is unavailable. Required: Redis `SET key value NX EX ttl` (or equivalent atomic shared primitive), reject on reuse, fail closed on store error, account for assertion expiry plus skew, and never fall back to process-local state in production.
- **F-S02 (Critical) — Evidence writes are unlinked and over-privileged.** `FrappeEvidenceSink.persist` (`evidence_store.py:53-88`) accepts an application reference from the decision record, inserts the evidence row, then updates that application's custom fields without proving the application exists in the expected ownership scope, that the evidence row is linked to it, or that the caller is authorized for it. A bug or a compromised agent process can attach evidence to an unrelated borrower's application or overwrite `custom_latest_evidence`. There is no audit log of who wrote which evidence.
- **F-S03 (High) — Conversation rebinding.** `_touch_conversation` overwrites `application` on an existing thread without checking the previous binding (`api/agent.py:43-48`). A thread created for application A can silently become a thread for application B; any history or system prompt that assumes the old binding can cross application context.
- **F-S04 (Medium) — AG-UI thread claim is not reconciled with the run's thread id.** `api/agui.py:34-53` authenticates and fixes the application from the assertion but streams using `RunAgentInput.thread_id`. The mint step checks ownership, so cross-borrower abuse is blocked; the missing check is equality between the asserted thread and the thread used for the run/events.
- **F-S05 (Medium) — Feedback DocPerm bypasses API validation.** `borrower_feedback.json:28` grants `Loan Borrower` create; a direct REST create can supply an arbitrary `application` and bypass rating/category/length/ownership checks unless the controller repeats them.
- **F-S06 (Medium) — `list_document_types` has no borrower context.** Any authenticated user can enumerate the document-type master. Sensitivity is low, but the method is inconsistent with every other borrower method.
- **F-S07 (Medium) — Invitation token in URL query.** The token is single-use and hashed at rest, but URL carriage exposes it to browser history, referrer headers and proxy logs before redemption.
- **F-S08 (Medium) — Trusted proxy headers are asserted, not tested.** The front door pins `Host` and `X-Frappe-Site-Name`, which is correct for the harness. There is no negative test showing that a forged header from a client cannot select a site or identity if the app is reachable around the proxy. Production must enforce this at the only ingress.
- **F-S09 (Medium) — Bureau execution has no per-user budget.** `/api/bureau/run` is gated by a valid assertion for an owned application, but a borrower can trigger repeated provider calls and evidence writes within the 60 s window and across mints. Provider cost and abuse controls are undefined.
- **F-S10 (Low) — Trace files contain decision detail on local disk.** Trace names are content hashes and files are private, but retention, encryption and access ownership are unspecified.

### 3.4 Duplicate implementation

- **F-D01 — Two lifecycle vocabularies.** Portal select includes `DRAFT` and is the field default; canonical machine starts at `SUBMITTED` and has explicit transitions. Nothing prevents the portal from writing a state the canonical machine cannot leave, and nothing prevents the sink or an administrator from writing a native status the mapping does not explain.
- **F-D02 — Two sources of lifecycle truth.** `custom_lifecycle_state` is portal-owned; native `status` is Lending-owned. The mapping is partial (only APPROVED/REJECTED, only drafts) and one-way.
- **F-D03 — One identity for two trust levels.** `FrappeClient` is documented as a read adapter but exposes `create` (`frappe_adapter.py:138`), and `evidence_store.py` reuses the same client/credential for privileged writes. The agent runtime constructs the same client, so read, write and test paths share one identity.
- **F-D04 — Dead conversation bookkeeping.** `record_turn` and `list_conversations` duplicate the thread metadata already written by `_touch_conversation`, but the live path never calls them, so `turn_count` is not maintained.
- **F-D05 — Assertion verification exists in both Frappe and FastAPI.** The Frappe `verify` is explicitly test-only and correctly documented; this is acceptable duplicated test surface, not a production path.

### 3.5 Unused routes and dead code

- **F-U01** — `record_turn` (`api/agent.py:77`) is called only by `tests/test_agent_bridge.py`.
- **F-U02** — `list_conversations` (`api/agent.py:100`) is called only by `tests/test_agent_bridge.py`.
- **F-U03** — `require_selected_application` (`portal/identity.py:137`) has no caller.
- **F-U04** — `FrappeEvidenceSink.get_record` is used only by tests/read paths; the live flow does not verify the row it just wrote by reading it back.
- **F-U05** — `FrappeClient.create` is unused by the P0 read path and contradicts the adapter's stated role.
- **F-U06** — `/api/chat` is not dead: the voice worker selects it when streaming is disabled (`apps/voice/agent_worker.py:224`). Do not remove it on the assumption that the island is its only caller.

### 3.6 Missing authorization checks

- **F-Z01** — Evidence sink: no application↔evidence linkage, no ownership re-check, no least-privilege service identity (B2).
- **F-Z02** — Feedback: direct REST create bypasses API ownership/validation (B4).
- **F-Z03** — `list_document_types`: authenticated but not borrower-scoped (B4).
- **F-Z04** — AG-UI: asserted thread and run thread are not compared (B5).
- **F-Z05** — `/api/bureau/run`: valid assertion plus owned application only; no role, budget or rate check (B4/F).
- **F-Z06** — Voice exchange: service credential is a shared static API key/secret; no rotation, scoping or per-session proof beyond the row check (C).
- **F-Z07** — Proxy: site identity comes from headers; enforcement is delegated to infrastructure with no test (B4/F).

### 3.7 Inconsistent data ownership

- **F-O01** — Evidence row's `loan_application` is not validated against the decision context or any authorization boundary.
- **F-O02** — `custom_latest_evidence` is a single mutable back-link; no history of which evidence was current when.
- **F-O03** — Conversation `application` is mutable while `user`/`customer` are fixed at creation; a relinked profile leaves old threads attached to the old customer.
- **F-O04** — Withdrawal of a submitted application leaves native `status = Open` while portal state is `WITHDRAWN`.
- **F-O05** — Timeline is synthesized presentation data, not an owned audit record.

### 3.8 Test gaps

- **F-T01** — No shared-store replay tests: first use, same-worker reuse, different-worker reuse, concurrent replay with exactly one winner, expiry, malformed, wrong issuer/audience, store-unavailable fail-closed, fresh valid token. (B1)
- **F-T02** — No evidence-linkage or least-privilege tests proving valid persistence, rejection of unrelated applications, no arbitrary Customer/Loan Application writes, no decision modification, borrower write denial and no System Manager requirement. (B2)
- **F-T03** — No canonical lifecycle transition/synchronization tests across portal and Lending states, including post-submit and withdrawal. (B3)
- **F-T04** — No proxy header-forgery negative test and no test that the front door is the only ingress. (B4/F)
- **F-T05** — No thread creation, reload/resume, identity change, cross-borrower denial or application-switch isolation tests. (B5)
- **F-T06** — No voice UI, consent, permission-denied, reconnect, hang-up or live-room test; exchange is mocked only. (C)
- **F-T07** — No automated accessibility run and no responsive proof at 768×1024, 1024×768, 1360×900 or wider. (E)
- **F-T08** — No two-worker FastAPI test and no load test for dashboard, list, detail, mint, streaming or conversation writes. (F)
- **F-T09** — Browser journey/security suites are not in the default suite and were not rerun in this audit; the execution report's 36/36 and 39/39 are historical. (H)
- **F-T10** — The E2E seed writer holds System Manager + Loan Manager, so it proves the flow works with elevated rights, not with the intended least-privilege identity. (B2/H)
- **F-T11** — No test that unsupported locales are rejected or surfaced rather than silently mapped to `en`. (G)
- **F-T12** — No test that a rejected/resubmitted correction path preserves submitted-document protections, because the path does not exist. (B3/D)

### 3.9 Production-only requirements

- **F-P01** — A shared atomic replay store (Redis or equivalent) with availability and fail-closed semantics.
- **F-P02** — A dedicated least-privilege evidence identity: create/read on `Loan Decision Evidence`, read on `Loan Application`, no Customer write, no decision write, no System Manager; documented key rotation.
- **F-P03** — A production reverse proxy that pins site/identity headers, terminates TLS, forwards cookies and CSRF, disables buffering for SSE and supports the LiveKit/WebSocket path. The current nginx file is a dev harness.
- **F-P04** — LiveKit server, TURN, worker deployment, room lifecycle, token grants and secret management.
- **F-P05** — Multiple uvicorn workers sharing the replay store; no process-local fallback.
- **F-P06** — SMTP or an identity provider for reset/verification (owner decision).
- **F-P07** — Secret management for `agent_assertion_secret`, LiveKit keys, service credentials and LLM/Langfuse keys.
- **F-P08** — Private-file backing, backups and retention for documents and evidence traces.
- **F-P09** — Per-user/IP rate limits and bureau budgets.
- **F-P10** — CSP/HSTS/frame-ancestors and production security headers.
- **F-P11** — Invitation email deliverability or a documented operator hand-over process.

## 6. Audit conclusion

The migrated platform is a working prototype with real end-to-end behavior: Frappe owns accounts, invitations, applications, documents and evidence storage; the Node runtime mints short-lived assertions; FastAPI verifies them and runs the same ZEN and LangGraph pipeline; and the browser island streams real answers. The execution report's core architecture claims are accurate.

It is **not production-ready**. Three defects block it: the assertion replay guarantee is per process (F-S01), the evidence write path is over-privileged and unlinked (F-S02), and the portal and Lending have two unreconciled lifecycle machines (F-D01/F-D02). Voice is server scaffolding without a user surface, conversation history is not wired, and most of the public/account and decision-support screens required by the next-phase brief are absent.

No recommendation in this audit is a style rewrite. Every action is limited to correctness, security, ownership, completeness or proof, and no working behavior should be replaced merely to change its shape.
