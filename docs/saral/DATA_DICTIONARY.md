# Saral data dictionary (rule inputs)

> **DRAFT, design only.** Generated by `python -m contracts.catalogue_v2.build` from `contracts/catalogue_v2/`. Nothing here is wired into ZEN, and nothing here is live. Bajaj Finance is a *public reference lender, not a partner*. ZEN is the authority for decisions; Bajaj's published numbers are indicative public guidance (user, 2026-11-03 23:07 IST).

Machine-readable: [`contracts/data_dictionary.json`](../../contracts/data_dictionary.json). 229 distinct input fields across 128 rules. Frappe locations were read from the doctype JSONs, `install.py` custom fields and the writers (`api/applications.py`, `api/profile.py`, `api/documents.py`, `api/evidence.py`) at 716db49. Native Loan Application fields come from Frappe Lending version-16, which is not vendored in the repo, so only the fields the portal writes are verified.

## RAG boundary

**The versioned ZEN catalogue JSON (`docs/saral/rule_catalogue.v2.json`) is the single source of truth for rules and thresholds.** RAG must never index the catalogue, this dictionary, `THRESHOLD_APPROVALS.md` or any prototype threshold. The agent gets decision reasons only from the stored decision through its tool (rule hits -> borrower category). An underwriter lookup is an exact lookup by `rule_id` in the JSON, never a vector search. See [ZEN_RAG_CONSISTENCY.md](ZEN_RAG_CONSISTENCY.md).

## Storage tiers (hybrid model)

- **LMS_SNAPSHOT**: Kept immutable with the decision record for the life of the application plus the owner's retention period (PROPOSED 8 years after closure or decline; UNVERIFIED: the G1 corpus states no period, and Bajaj's privacy policy says 'Storage of data as per company's policy in addition to regulatory and legal requirements', BFL-PRIVACY#003).
- **SOURCE_REFERENCE**: Raw payload stays at the synthetic API / object store (PROPOSED 180-day TTL for synthetic data); the LMS keeps reference id, sha256 and fetch time as LMS_SNAPSHOT.
- **NEVER_STORE**: Held in memory for the request only; never written to the LMS, logs or traces.

Signature results (presence, crop hash, similarity, anomaly score, REFER flag) are LMS_SNAPSHOT; the signature image is SOURCE_REFERENCE.

## PII classes and masking

| Class | Rule |
|---|---|
| NONE | Not personal. No masking. |
| PERSONAL | Personal data. Borrower and authorised staff only; never in logs, traces sent to observability, or LLM prompts. |
| CONTACT | Contact data. As PERSONAL; cross-applicant matching uses a salted sha256 hash only. |
| GOV_ID | Government identifier. PAN as XXXXX1234X, Aadhaar as last 4 digits; the full number is NEVER_STORE. |
| FINANCIAL | Financial data. Underwriter role; borrower sees own values; LLM sees only Decision Evidence values; never in logs. |
| CREDIT | Bureau data (synthetic). Underwriter role; the borrower is told categories, never bureau line items by the agent. |
| INTERNAL_RISK | Risk signal. Underwriter role only; never shown to the borrower or used in borrower-facing text. |
| BIOMETRIC_LIKE | Signature-derived. LMS keeps presence, crop hash and scores only; the image stays at the source with a short TTL. |

## Never stored

| Item | PII | Handling |
|---|---|---|
| Full PAN typed in step 2 | GOV_ID | Used in memory for the synthetic PAN and bureau calls, then dropped; LMS keeps pan_masked + pan_hash. |
| Full Aadhaar number | GOV_ID | Never requested or accepted. The synthetic Aadhaar API returns last 4 + verification status. |
| OTP codes | NONE | Never stored or logged. |
| Raw OCR text of documents | PERSONAL | PR #41 masks before values reach a dataclass; raw text is not kept. |
