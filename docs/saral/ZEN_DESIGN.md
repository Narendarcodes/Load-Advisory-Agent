# Saral ZEN design: personal loans by purpose

**Status: DESIGN DRAFT. Nothing in this document is live.** The thresholds in force are still the four synthetic rules in `decision_engine/policies/personal_loan_synthetic_v1.json` (income ₹25,000, FOIR 0.45, score 700, employment 12 months). This document proposes what replaces them. Every row tagged **ASSUMPTION** stays pending until the owner approves it in [THRESHOLD_APPROVALS.md](THRESHOLD_APPROVALS.md).

| | |
|---|---|
| Lender | **Bajaj Finance Ltd**, a *public reference lender, not a partner*. It is the only lender. |
| Products | Four personal-loan subcategories, by purpose: `PL_WEDDING`, `PL_HIGHER_EDUCATION`, `PL_HOME_RENOVATION`, `PL_MEDICAL_EMERGENCY`. |
| Division of work | **ZEN decides. RAG and the agent explain.** The agent never changes an outcome. |
| Data | Synthetic only: synthetic bureau, synthetic documents, `SYN-` ids. |
| Contracts | `contracts/` (pydantic, with JSON Schema exported to `contracts/schemas/`). |
| Draft rule catalogue | `docs/saral/rule_catalogue.draft.json` (machine-readable copy of §3–§6, generated by `contracts/fixtures/build_fixtures.py`). |
| Source citations | corpus_v3 `saral_nbfc_policy`, chunk ids `<DOC>#<NNN>` (branch `feat/saral-corpus-collections` @ `3de95b0`, local and not yet merged). Excerpts in the catalogue were checked word for word against those chunks. |

Tags used in every table:

- **BAJAJ-SOURCED**: the number is stated in a Bajaj document. The chunk is named.
- **ASSUMPTION**: Bajaj states no number. The value is a Saral proposal with an id `A-NN`, and it needs the owner's approval. When Bajaj *names* the criterion without a number (for example "High FOIR (as per lender criteria)"), that chunk is given as *context*. Context does not make a threshold sourced.

## 2. Data-point catalogue

ZEN reads one flat object, `ZenInput.data_points`, keyed by `DataPointName` in `contracts/zen.py`. Every key is always present. A missing value is `null` with `source = NONE`. Every value carries its `source`, `fallback_used`, `low_confidence` and `source_document_ids`. Raw documents, raw bureau JSON and identity numbers never reach ZEN, and the contract rejects any string that looks like a full PAN or Aadhaar.

### 2.1 Catalogue

| Data point | Formula / derivation | Primary source | Fallback when missing |
|---|---|---|---|
| `loan_amount`, `tenure_months`, `purpose` | As applied | Application | None. These are required; the application cannot be submitted without them. |
| `age_at_application` | Completed years from the applicant record's `date_of_birth` to the application date | Applicant record | PAN or Aadhaar DOB from OCR (`fallback_used`); otherwise `null` → REFER |
| `age_at_maturity` | `age_at_application + tenure_months / 12`, rounded up | Computed | `null` if age is missing |
| `nationality` | ISO code on the applicant record | Applicant record | `null` → REFER |
| `employer_category` | PUBLIC / PRIVATE / MNC / OTHER | Applicant record; employer name from the employment letter or payslip OCR | `null` → REFER |
| `employment_months` | Months with the current employer: `employment_months` from the employment letter (PR #41 computes it from `employment_start_date`) | OCR, employment letter | Declared value (`fallback_used`, REFER through B12's missing path if neither) |
| `payslip_net_avg` | Mean `net_salary` over the payslips supplied (Bajaj asks for 3) | OCR, salary slip | `gross_salary × (1 − deductions/gross)` when `net_salary` is missing but `total_deductions` was read; otherwise `null` |
| `bank_salary_credit_avg` | `salary_credits ÷ salary_credit_months` from the bank statement | OCR, bank statement | `null` |
| **`net_monthly_income`** (A-01, A-02) | `min(payslip_net_avg, bank_salary_credit_avg)` when both exist. If only one exists, that one, with `fallback_used`. | Computed | Employment-letter `monthly_gross` (`fallback_used`, and B19 is NOT_EVALUATED → REFER). Then the declared income (REFER). Self-employed: see §6. |
| **`income_variance_ratio`** (A-11) | `abs(payslip_net_avg − bank_salary_credit_avg) / payslip_net_avg` | Computed | `null` when either side is missing → B19 NOT_EVALUATED → REFER |
| **`existing_emi_total`** (A-06) | Σ `emi` over ACTIVE bureau tradelines. For a revolving line (card, overdraft) whose reported EMI is 0 and whose balance is above 0: `max(emi, 5% × current_balance)` | Bureau | Declared obligations (`fallback_used`) when the bureau is NO_HIT or failed; otherwise `null` → REFER |
| **`proposed_emi`** (A-05) | Bajaj's EMI formula with `R = assessment_rate / 12` and `n = tenure_months`. Proposed assessment rate: 20% a year | Computed | `null` only if the amount or tenure is missing |
| **`foir`** (A-04) | `(existing_emi_total + proposed_emi) / net_monthly_income`. **This changes the definition**: the synthetic v1 rule left the new EMI out (`monthly_obligations / monthly_income`). | Computed | `null` when income or obligations are missing → B11 NOT_EVALUATED → REFER. `low_confidence` is inherited from income. |
| `credit_score` | `score.value` | Bureau (synthetic score, not CIBIL) | `null` when the score status is NO_HIT or INSUFFICIENT_HISTORY → NEW_TO_CREDIT segment |
| `max_dpd_12m`, `max_dpd_24m` | Worst DPD bucket floor (0/30/60/90) across all tradelines in the window | Bureau | `0` for NO_HIT; `null` when the bureau failed → REFER |
| `enquiries_6m` | Count of enquiries dated within 6 months before the report date | Bureau | as above |
| `writeoff_settlement_24m` / `_older` | Any WRITTEN_OFF or SETTLED tradeline with `status_changed_on` within 24 months / before that | Bureau | as above |
| **`salary_credit_months`** (A-12) | PR #41 `salary_credit_months` from the bank statement | OCR, bank statement | `null` → B20 NOT_EVALUATED → REFER |
| **`debit_credit_ratio`** (A-13) | `total_debits / total_credits` over the statement period | OCR, bank statement | `null` → B21 NOT_EVALUATED → REFER |
| **`kyc_name_match_score`** (A-14) | The lowest pairwise similarity across the applicant record name, PAN `name`, Aadhaar `name`, payslip `employee_name` and bank `account_holder`. Similarity is the normalised token-set ratio (0..1) after case-folding and dropping honorifics. Initials match their full name. | OCR (multi) | The existing KYC record for EXISTING_CUSTOMER (§6); otherwise a comparison over the names available, and `null` if fewer than 2 → REFER |
| **`kyc_dob_match`** (A-15) | Applicant DOB = PAN DOB = Aadhaar DOB, over those present (an Aadhaar card printing only a year matches on the year) | OCR (multi) | as above |
| **`kyc_id_last4_match`** (A-15) | Last 4 digits of the masked PAN from OCR = the record's `pan_masked` digits, **and** the OCR Aadhaar last 4 = the record's `aadhaar_last4` | OCR (multi) | as above |
| `required_docs_present` | KYC document + PAN + 3 salary slips + 3 months of bank statements, each with a non-empty extraction (salaried). The self-employed list is in §6. | Computed | Never `null` |
| **`min_ocr_confidence`** (A-16) | The lowest `ocr_confidence` over the OCR fields **that fed a rule** in this decision. Fields no rule reads, such as a bank `closing_balance`, do not count. | Computed | `null` when no OCR field was used (for example, every value is declared) → S01 NOT_EVALUATED → REFER |
| **`signature_similarity`** (A-17) | `SignatureCheck.similarity` (0..1). The application signature is compared with the PAN-card signature. Experimental: no module exists yet. | Signature check | `null` → S02 NOT_EVALUATED → **NO_EFFECT** (S02 is not required) |

`low_confidence` is set on a data point when any OCR field it was computed from has PR #41 status `low_confidence` or `invalid`, or a confidence below the S01 floor. It propagates through formulas: if income is low confidence, so is FOIR.

### 2.2 Bank health, income cross-check and KYC consistency in one place

- **Income cross-check** = B19 on `income_variance_ratio`. Net pay should land almost exactly in the salary account; the 10% tolerance (A-11) allows for reimbursements and arrears.
- **Bank health** = B20 (salary credited in each of the 3 statement months, A-12) + B21 (debits not above credits, A-13). Bounce counts and average balances are **not extracted by PR #41**, so they are not data points yet. Adding them is a PR #41 follow-up, not a ZEN change.
- **KYC consistency** = B22 (name, A-14) + B23 (DOB) + B24 (PAN/Aadhaar last 4, A-15). Bajaj names "Document mismatched" as a rejection reason (BFL-PL-OVERVIEW#018). Saral **refers** on a mismatch instead of declining, because an OCR misread looks exactly like a mismatch.

## 5. Signature similarity and OCR confidence: screening only

Both enter ZEN only as **SCREENING** rows (S01, S02) and through the `low_confidence` flag. The contract enforces three properties (`contracts/decision_trace.py`):

1. **A SCREENING rule can only REFER.** `on_fail = DECLINE` on a SCREENING row is a validation error.
2. **Low confidence never declines.** If a rule whose effect is DECLINE fails on a value marked `actual_low_confidence` (OCR-derived, or computed from OCR such as FOIR), the row's outcome becomes **REFER** with `downgraded_from = DECLINE`. A human sees the document before anyone is declined on a misread digit. Example: fixture `zen_output_refer_low_confidence.json`, where FOIR is 1.0065 against 0.50 but the income came from a payslip read at 55% confidence.
3. **Signature is optional.** No signature module exists. A missing similarity is `NOT_EVALUATED` with **NO_EFFECT**. A present similarity below 0.80 REFERs. Bureau values cannot be marked low confidence.

The OCR floor (A-16) reuses PR #41's own `LOW_CONFIDENCE = 60.0`, so a field PR #41 shows as "check this" is the same field ZEN refers on. The PR #41 constant is an OCR engineering value and stays separate from the approval-pending ZEN floor.

## 6. Segmentation

Segments do not decide anything. They select a threshold, add or skip a rule, or change an effect, and every change carries its own basis tag (`contracts/segment.py`). An applicant has exactly one EMPLOYMENT_GEO segment, at most one CREDIT segment (none when the score is below 650, which B09 declines), and optionally EXISTING_CUSTOMER. When two segments set the same threshold, the more conservative value wins (A-30). With the current set this never happens, but the precedence is fixed so that future segments cannot loosen a rule by accident.

| Segment | Dimension | Assigned when | What it changes | Basis |
|---|---|---|---|---|
| SALARIED_METRO | EMPLOYMENT_GEO | Salaried and lives in Pune, Bengaluru, Mumbai or Delhi (A-03) | B10 threshold → **40,000** | BAJAJ-SOURCED (BFL-PL-SALARIED#012); the city list is A-03 |
| SALARIED_NON_METRO | EMPLOYMENT_GEO | Salaried, any other city | B10 threshold → **25,001** | BAJAJ-SOURCED (BFL-PL-SALARIED#004). Bajaj says the figure is "based on the city", and only the floor and the metro figure are published. |
| SELF_EMPLOYED | EMPLOYMENT_GEO | `employment_type = SELF_EMPLOYED` (a profile Bajaj lists, BFL-PL-ELIG-DOCS#007) | Income = average monthly bank credits over the statement period; B10 floor 25,001 on that; skips B08, B12, B19, B20; required docs = KYC + PAN + 6 months of statements; adds **SE01_MANUAL_INCOME_REVIEW**, which always REFERs, because no ITR or business-proof OCR exists | ASSUMPTION **A-23** |
| PRIME | CREDIT | Score ≥ 750 (A-20) | B11 threshold → **0.55** | ASSUMPTION **A-21** |
| NEAR_PRIME | CREDIT | 650 ≤ score ≤ 749 (A-20) | Nothing; base thresholds apply | ASSUMPTION **A-20** (band boundary only) |
| NEW_TO_CREDIT | CREDIT | Score status NO_HIT or INSUFFICIENT_HISTORY | B09 is NOT_EVALUATED → REFER (never auto-approve, never decline for having no history); B13–B18 evaluate on an empty history; B11 threshold → **0.40**; adds **NTC01_INDICATIVE_AMOUNT_CAP** ₹2,00,000 for the reviewer | ASSUMPTION **A-22** |
| EXISTING_CUSTOMER | RELATIONSHIP | `existing_customer = true` on the synthetic record | B22–B24 may read the existing KYC record (`source = EXISTING_KYC`) instead of OCR. **No threshold is relaxed.** | Reuse of KYC is BAJAJ-SOURCED (BFL-APP-TNC-2023#012); "no relaxation" and the source swap are **A-24** |

## 7. Decision outcomes

| Outcome | When | What the applicant is told (agent, from the trace) |
|---|---|---|
| **APPROVE** | Every row is PASS or NO_EFFECT | That the application meets the draft criteria, with the numbers. While the policy is DRAFT, every output is stamped `not_for_live_use = true`. |
| **REFER** | No DECLINE row, and at least one REFER row: a REFER-effect failure, a missing required input, a screening flag, or a downgraded low-confidence DECLINE | What is needed, by rule: re-upload a clearer document, add the missing statement, confirm a mismatch. Missing data never declines. |
| **DECLINE** | At least one DECLINE row on a value that is not low confidence | Each failed rule with its actual value, threshold and source, and a concrete path to reapply (for example, reduce the amount so FOIR ≤ 0.50, or wait out a DPD window) |

`decision_from_rows` in `contracts/decision_trace.py` is the single definition: DECLINE beats REFER, and REFER beats APPROVE. `ZenOutput` rejects a decision or reason-code list that disagrees with its own trace. The bureau data-quality gate (`REVIEW`/`ERROR`) still runs before ZEN, as it does today, and is not a ZEN outcome.

```
        │
        ▼
 ZEN (zen-engine 2.1.2, one JDM model per product, draft) → saral-zen-output/1
        │            decision + reason codes + not_for_live_use
        ▼
 Decision trace (saral-decision-trace/1): one row per rule with actual, threshold, operator,
        │            result, outcome, basis, citation (doc id + chunk + ≤320-char excerpt) or assumption id
        ▼
 Agent explanation: reads the trace (PR #38 meters for >=/<= rows) and retrieves the cited
                    Bajaj chunk from saral_nbfc_policy (and RBI text from rbi_regulatory) to explain.
                    It never changes the outcome and never presents an ASSUMPTION as Bajaj policy.
```

Stated plainly:

- ZEN does not call the bureau or OCR. It reads `ZenInput` only.
- The agent does not call ZEN to decide. It explains a stored `ZenOutput`.
- An ASSUMPTION row is explained as "Saral's proposed rule, not a Bajaj figure".
